## 1. บริบทและที่มาของปัญหา (Context & The 160GB Bloat Problem)

ในระหว่างการวิจัยระบบวิศวกรรมย้อนกลับของเอนจิน Kirikiri Z สำหรับเกม Senren＊Banka (千恋＊万花) ตั้งแต่ช่วงเริ่มต้น (Step 01 จนถึง Step 42) ได้มีการสร้างสภาพแวดล้อมรันไทม์จำลอง (Isolated Runtime Environments) ใน `archive/historical_builds/` เพื่อทดสอบแยกชิ้นส่วนแบบ Sandbox เช่น:
- การทดสอบการถอดรหัส PSB (`runtime_test_step12`, `step15`, `step18`)
- การทดสอบ Canary Injection และ TJS Hooking (`step21`, `step24`, `step26`, `step27`, `step28`)
- การวิเคราะห์ตัวเกม Steam DRM (`step23_analysis`)
- การทดสอบฟอนต์ไทยและการเรนเดอร์ (`step36_thai_rendering_test`)

เนื่องจากเอนจินเกมต้องการไฟล์ทรัพยากรหลัก (`.xp3`) ในการบูต แต่ละโฟลเดอร์ทดลองจึงมีการคัดลอกไฟล์ `.xp3` ของตัวเกมขนาด ~10 GB ซ้ำกันไปถึง 13 โฟลเดอร์ ส่งผลให้:
1. **การกินพื้นที่ดิสก์อย่างมหาศาล:** พื้นที่โฟลเดอร์พุ่งสูงถึง **159.89 GB** โดยเป็นไฟล์ `.xp3` ซ้ำซ้อนกันใน `archive/` สูงถึง **~142 GB (93.3% ของทั้งโปรเจกต์)**
2. **ความรกและกระจัดกระจายที่ Root Directory:** ไฟล์ Backup ของ Excel, ไฟล์ขยะชั่วคราว (`C2310500`), และไฟล์ JSON Dump ชั่วคราวถูกเซฟทิ้งไว้ที่โฟลเดอร์หลัก
3. **โฟลเดอร์เครื่องมือ (`tool/`) ขาดความชัดเจน:** มีสคริปต์ปะปนกันถึง 96 ไฟล์ โดยแบ่งเป็นสคริปต์หลักที่ใช้งานจริง 17 ไฟล์ และสคริปต์วันออฟเฉพาะตอนในอดีตอีก 79 ไฟล์

## 2. หลักการและข้อตกลงในการจัดการ (Refactoring Philosophy)

การจัดระเบียบและทำความสะอาดในโครงการวิศวกรรมย้อนกลับขนาดใหญ่ จำเป็นต้องยึดหลัก **"Preserve Evidence & Maintain Reproducibility"** อย่างเคร่งครัด:

1. **Rule 1: ห้ามลบหลักฐานที่เป็นภูมิปัญญา (Never Delete Intellectual Property / Evidence)**
   - โค้ดสคริปต์ Python (`.py`), สคริปต์เอนจิน (`.tjs`), ข้อมูลวิเคราะห์ (`.json`, `.txt`), ล็อกไฟล์กระบวนการ (`.log`, Procmon) ทุกไฟล์ตั้งแต่ Step 12-40 **ต้องคงอยู่ 100%**
2. **Rule 2: แยกแยะระหว่าง "ไฟล์สร้างใหม่ได้" กับ "ข้อมูลที่มีคุณค่าทางประวัติศาสตร์"**
   - ไฟล์เกม `.xp3` ในโฟลเดอร์ทดสอบเก่า สามารถลบได้ เพราะเรามี `archive/original_game_backup/` (Clean 10.2 GB) และ `SenrenBanka_THAI_PLAYABLE/` (Production 10.2 GB) ไว้อย่างสมบูรณ์
   - แคชไคลเอนต์ Python (`__pycache__`) เป็นไบนารีที่คอมไพล์ใหม่ได้ตลอดเวลา
3. **Rule 3: จัดระเบียบด้วยการ "ย้ายเข้าหมวดหมู่" แทนการลบทิ้ง (Archive & Categorize)**
   - ไฟล์ Excel สำรองและสคริปต์ batch ในอดีต ให้ย้ายไปรวมไว้ในโฟลเดอร์ประวัติศาสตร์เฉพาะด้าน

## 6. บทเรียนที่ได้รับ (Lessons Learned)

1. **Sandbox Cloning Hazard:** เมื่อจำเป็นต้องโคลนเอนจินขนาดใหญ่ (>10 GB) เพื่อทดสอบรันไทม์ ควรวางแผนกำหนด Lifecycle ไว้ล่วงหน้า เมื่อการวิจัยสรุปผลจนได้ผลลัพธ์ที่แน่นอนแล้ว ควรปลดปล่อยไฟล์ไบนารีขนาดใหญ่ออกทันที โดยเก็บรักษาเฉพาะ Source Code, Logs และ Config ไว้
2. **Automated Cache Bloat:** การรันสคริปต์จำนวนมากสร้างโฟลเดอร์ `__pycache__` ซ้ำซ้อนกระจายตัวในทุกระดับโฟลเดอร์ ควรมี Routine สคริปต์สำหรับทำความสะอาดเป็นระยะ
3. **Root Cleanliness Discipline:** โฟลเดอร์ Root ควรมีเฉพาะไฟล์สำหรับ End-User หรือจุดเริ่มต้นของระบบ (Single Source of Truth) เพื่อลดโอกาสที่ผู้พัฒนาหรือเครื่องมือภายนอกจะหยิบไฟล์สำรองเก่าไปใช้งานผิดพลาด
