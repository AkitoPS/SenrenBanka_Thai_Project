# กรณีศึกษาที่ 03: กับดัก `TVP_ARCHIVE_ONLY` และการใช้ Process Monitor แกะรอย
## (Case Study: The `TVP_ARCHIVE_ONLY` Trap & Empirical ProcMon Investigation)

---

## 1. สมมติฐานแรกที่ล้มเหลว (The Failed Assumption)

ในขั้นตอนการแก้ปัญหาฟอนต์ภาษาไทยและสคริปต์ในช่วงแรก เราตั้งสมมติฐานตามแนวทางของเกม Kirikiri Z ทั่วไป:
1. *"ถ้าวางไฟล์หลวม `font/font1_32.tft` หรือ `font/NotoSansThaiLooped.ttf` ไว้ในโฟลเดอร์เกม เอนจินจะอ่านไฟล์บนดิสก์ก่อน Archive เสมอ"*
2. หรือ *"ถ้าสร้าง `patch2.xp3` เพิ่มขึ้นมาอีกไฟล์ เอนจินจะโหลดต่อจาก `patch.xp3` เสมอ"*

**ความเป็นจริงที่พบ:**
- ผู้ใช้นำไฟล์ฟอนต์ไปวางตามคำแนะนำ แต่ตัวเกม**ไม่มีอะไรเปลี่ยนแปลงเลยแม้แต่น้อย** ฟอนต์ยังคงเป็นฟอนต์เดิม และบทพูดยังคงเป็นภาษาเดิม เหมือนกับว่าเกมมองไม่เห็นไฟล์เหล่านั้น

---

## 2. การใช้ Process Monitor (ProcMon) เพื่อหาความจริงเชิงประจักษ์

เพื่อให้เห็นการทำงานจริงของตัวเกมระดับ System Call เราจึงให้ผู้ใช้รันเกมผ่านโปรแกรม **Process Monitor** ของ Microsoft Sysinternals เพื่อบันทึกพฤติกรรมของ `SenrenBanka.exe` ออกมาเป็นไฟล์ [`report2.CSV`](file:///c:/Users/DELL/Desktop/VN_Thai_Project/archive/logs_and_dumps/report2.CSV) (ขนาด 12 MB, จำนวนแสนบรรทัด):

### ข้อมูลสำคัญที่ค้นพบจาก ProcMon Log:

1. **ตัวเกมไม่เคยพยายามเปิดไฟล์หลวมเลย (Zero Loose File Access):**
   - เมื่อค้นหาคำว่า `font/font1_32.tft` ในคอลัมน์ Path ไม่มี System Call คำสั่ง `CreateFileW` หรือ `FASTIO_READ` ไปยังโฟลเดอร์เกมภายนอกเลยแม้แต่ครั้งเดียว
   - เอนจินทำงานในโหมด **`TVP_ARCHIVE_ONLY`** ซึ่งถูกฮาร์ดโค้ดไว้ในตัว Executable ปิดการเข้าถึงดิสก์โดยตรงโดยสิ้นเชิง
2. **ตัวเกมแตกฟอนต์จาก `data.xp3` ลง `%TEMP%` เสมอ:**
   - ใน ProcMon ปรากฏหลักฐานชัดเจน:
     ```text
     SenrenBanka.exe IRP_MJ_CREATE C:\Users\DELL\AppData\Local\Temp\krkr_c1bbbab76455_28147564_23708\font1_32.tft SUCCESS
     SenrenBanka.exe IRP_MJ_WRITE  C:\Users\DELL\AppData\Local\Temp\krkr_c1bbbab76455_28147564_23708\font1_32.tft SUCCESS
     ```
   - ก่อนจะแสดงตัวหนังสือ ตัวเกมจะอ่านไบต์จาก `data.xp3` แล้วถอดรหัสออกมาเขียนลงในโฟลเดอร์ Temp ชั่วคราว แล้วจึงโหลดเข้าสู่อินเทอร์เฟซ GDI
3. **การเพิกเฉยต่อชื่อไฟล์ใหม่:**
   - การสร้างไฟล์ชื่อแปลกๆ เช่น `patch2.xp3` ถูกเอนจินเพิกเฉย เพราะเอนจินมีรายชื่อไฟล์คลังที่อนุญาต (Hardcoded Whitelist) ชัดเจน เช่น `patch_extra.xp3`, `patch_z.xp3`, `patch.xp3`, `data.xp3` เท่านั้น

## 3. ทางออกทางวิศวกรรม (The Proven Solution)

เมื่อทราบความจริงจาก System Call เราจึงเปลี่ยนยุทธวิธีอย่างสิ้นเชิง:
1. **เลิกพยายามใช้ไฟล์หลวมบนดิสก์:** ไม่วางไฟล์ในโฟลเดอร์ `font/` อีกต่อไป
2. **ฉีดเข้า `data.xp3` โดยตรง (Native Injection):**
   - ในเมื่อเกมบังคับแตกฟอนต์จาก `data.xp3` เราจึงต้องผ่าตัดโครงสร้างของ `data.xp3` เพื่อนำฟอนต์ภาษาไทยขยายเข้าไปแทนที่ไบนารีเดิมในคลังเกมหลัก
3. **ใช้เฉพาะชื่อ Archive ที่อยู่ในระบบ:**
   - สำหรับบทสนทนา ให้ใช้ชื่อ **`patch_extra.xp3`** ซึ่งเป็นชื่อที่เอนจินให้ลำดับความสำคัญสูงสุดในการโหลด

---

## 4. บทเรียนทางวิศวกรรมที่นำไปใช้ในอนาคต (Lessons Learned)

1. **อย่าเดาพฤติกรรมเอนจิน ให้ใช้ Process Monitor:**
   - หากเกมไม่โหลดไฟล์ที่เราแก้ อย่าเสียเวลาเดา ให้เปิด ProcMon กรองเฉพาะ Process Name ของเกม แล้วดูว่าเกมเรียก `CreateFile` ที่ Path ใด และเปิดไฟล์ใดจริงในระดับ OS
2. **Visual Novel ยุคใหม่ (โดยเฉพาะบน Steam) ปิด VFS ภายนอกเกือบทั้งหมด:**
   - ความเชื่อดั้งเดิมที่ว่า "วางไฟล์ข้างนอกจะทับไฟล์ข้างใน" ใช้ไม่ได้กับเกมที่คอมไพล์ด้วยแฟล็กความปลอดภัยสูง การฉีดลงใน Archive หลักคือวิธีเดียวที่การันตีความสำเร็จ 100%
