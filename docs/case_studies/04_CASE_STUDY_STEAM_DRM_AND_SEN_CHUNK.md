## (Case Study: Steam Digital Signatures, the `sen:` Chunk & XP3 Redirection)

## 1. ความล้มเหลวของเครื่องมือสาธารณะ (The Failure of Public Tools)

เมื่อเราต้องการแพ็กเกจไฟล์บทพูดหรือฟอนต์กลับเข้าเป็น `.xp3` เราได้ทดลองใช้เครื่องมือสาธารณะที่นิยมใช้ในวงการม็อดเกมญี่ปุ่น:
* **FreeMote (PsbDecompile / PsbBuild)**
* **XP3Tools / Kirikiri Tools**
* **ArcXP3**

**ผลลัพธ์ที่เกิดขึ้น:**
- ทันทีที่นำไฟล์ `.xp3` ที่สร้างจากเครื่องมือข้างต้นไปใส่ในเกม ตัวเกมจะ:
  1. ขึ้นกล่องข้อความแจ้งเตือน Integrity Error หรือ Signature Mismatch
  2. หรือแครชปิดตัวเองทันทีตั้งแต่โลโก้เปิดเกม (Crash on Startup)

## 2. การสืบสวนโครงสร้างไบนารีระดับลึก (Deep Binary Analysis)

เมื่อเรานำไฟล์ `.xp3` ต้นฉบับมาเปรียบเทียบกับไฟล์ที่สร้างจากเครื่องมือทั่วไป เราพบความแตกต่างสำคัญ 2 จุดใหญ่:

### จุดที่ 1: การมีอยู่ของ `sen:` Chunk และลายเซ็น Steam 24 ไบต์
เมื่อคลายการบีบอัด Index ของ Archive ต้นฉบับของ Steam ออกมา พบว่า **ก่อนหน้า Chunk `File` แรกสุด จะมี Chunk พิเศษขนาด 52 ไบต์ชื่อ `sen:`**:
```text
+-------------------------------------------------------------+
| 0..3 (4B):    b'sen:'                                       |
| 4..11 (8B):   Chunk Length = 40                             |
| 12..19 (8B):  hnfn_off (พิกัดตารางชื่อไฟล์)                 |
| 20..27 (8B):  hnfn_uncomp (4B), hnfn_comp (4B)              |
| 28..51 (24B): Steam Digital Signature                      |
|               b'\n\x00CSK`\n\xff\x07N\xb1\x82Steam\x00\x00\x00' |
+-------------------------------------------------------------+
```
* **บทบาทของลายเซ็นนี้:** เอนจิน Kirikiri Z รุ่นของ Steam จะตรวจสอบว่า 24 ไบต์นี้ตรงกับคีย์ที่คอมไพล์ไว้ใน `SenrenBanka.exe` หรือไม่ หากไม่มี Chunk นี้ หรือสตริง `Steam` หายไป เอนจินจะมองว่า Archive นี้เป็นของปลอมหรือถูกดัดแปลง และปฏิเสธการอ่านทันที
* **เครื่องมือทั่วไปล้มเหลวเพราะ:** เครื่องมือสาธารณะไม่รู้จักสเปกเฉพาะของ Yuzusoft จึงทิ้ง Chunk `sen:` ไป และเริ่ม Index ด้วย `File` ทันที

---

### จุดที่ 2: ระบบพอยน์เตอร์ Redirection 2 ชั้น (Offset 23 / 32)
ในสเปก XP3 ปกติ พิกัด Index ท้ายไฟล์จะถูกเขียนไว้ที่ไบต์ 11..18 (`hdr[11:19] = idx_off`)
แต่อนุสัญญาของ Yuzusoft บน Steam มีโครงสร้างที่ซับซ้อนกว่านั้น:
1. **ไบต์ 11..18 ไม่ใช่ตำแหน่ง Index** แต่เป็นตัวชี้ **`redir_off = 23`**
2. ที่ตำแหน่ง Offset 23 จะมีไบต์แฟล็ก `0x80` ตามด้วย Dummy Length 8 ไบต์
3. **ที่ตำแหน่ง Offset 32 (Offset 23 + 9) จึงจะเป็นตัวชี้ `real_idx_off` ที่แท้จริง**
4. หากนำโปรแกรมทั่วไปไปแพ็ก โปรแกรมจะเขียน Index ทับที่ Offset 11 ทำให้เอนจินเกมพยายามอ่านไบต์ 23 จากท้ายไฟล์ ส่งผลให้เกิด **End of File (EOF) Error** ทันที

## 3. ทางออกทางวิศวกรรม (The Custom Packaging Engine)

เราจึงเขียนเครื่องมือ Repacker ขึ้นมาใหม่ทั้งหมดด้วย Python ([`method/tools/pack_patch_extra.py`](file:///c:/Users/DELL/Desktop/VN_Thai_Project/method/tools/pack_patch_extra.py)):

1. **ดึง Chunk `sen:` ต้นฉบับมาคำนวณใหม่:**
   - คำนวณ `new_hnfn_off` ตาม Delta ขนาดไฟล์ที่เปลี่ยนไป
   - นำลายเซ็น Steam 24 ไบต์ดั้งเดิมมาประกบท้าย Chunk `sen:` อย่างสมบูรณ์ 40 ไบต์
2. **รักษา Redirection Table:**
   - คงค่าไบต์ 11 เป็น `redir_off = 23`
   - เขียนพิกัด `real_idx_off` ใหม่ลงที่ตำแหน่ง Offset 32 (ไบต์ `23 + 9`):
     ```python
     struct.pack_into('<Q', new_archive, redir_off + 9, new_real_idx_off)
     ```
3. **ผลลัพธ์:** ตัวเกมโหลดไฟล์ผ่านฉลุย 100% เอนจินตรวจพบลายเซ็น Steam ครบถ้วน ไม่มี Error ใดๆ ทั้งสิ้น

## 4. บทเรียนทางวิศวกรรมที่นำไปใช้ในอนาคต (Lessons Learned)

1. **อย่าไว้ใจเครื่องมือสำเร็จรูปกับเกมรุ่น Steam:**
   - เกมวิชวลโนเวลบน Steam มักมีเลเยอร์การป้องกัน DRM และการตรวจสอบความสมบูรณ์ที่เครื่องมือโอเพนซอร์สทั่วไปไม่ได้รองรับ การเขียน Repacker เฉพาะกิจระดับไบนารีที่รักษา Header ดั้งเดิมไว้คือทางเลือกที่เสถียรที่สุด
2. **ตรวจสอบ Header และ Pointer 2 ชั้นเสมอ:**
   - เมื่อเจอฟอร์แมต XP3 ในเกมค่าย Yuzusoft ให้ตรวจดูไบต์ 11 ก่อนเสมอ หากมีค่าเป็น `23` แสดงว่าเกมนั้นใช้ระบบ Redirection Table 2 ชั้นเช่นเดียวกัน
